# Factory de distribution : du contact à la conversion

[Retour à l'index](README.md)

## Architecture opérationnelle

Les humains se consacrent aux relations, partenariats, décisions commerciales et diffusion. Les agents peuvent préparer recherche, qualification, synthèses, messages, relances consenties, tableaux de bord et comparatifs. Ne pas automatiser des promesses, contrats, témoignages ou messages trompeurs. **Composer des outils CRM existants** avant d'en développer un nouveau.

Pipeline : **compte identifié → interlocuteur contacté → échange accepté → entretien tenu → besoin qualifié → partenariat accepté → preview/pilote activé → réusage → client Cloud payant**. À part : **référence autorisée** et **canal de distribution activé**. Chaque transition nécessite date, preuve, prochaine action et propriétaire.

## Messages d'approche (anglais)

**Développeur, sans preview encore disponible :**

> Hey! I noticed you're working with multiple coding agents. I'm exploring a Git coordination layer for concurrent sessions, especially stale state, merges and overlapping work. I'm talking with developers who already deal with this. Would you be open to a quick chat about your current workflow?

**Lead / CTO :**

> I'm researching how teams coordinate Git when multiple coding agents work across repositories and machines. Ruu aims to remove routine version-management overhead without requiring developers to reserve files or manually schedule merges. Would you be open to a brief conversation about the friction your team experiences?

**Quand une véritable démonstration est prête :**

> We're preparing a small private Ruu Core preview on isolated disposable Git repositories. Would you like to challenge the system with your real multi-agent scenarios, without giving it access to production code?

**Demande d'introduction avant produit :**

> Est-ce que tu connais une ou deux équipes confrontées au même problème ? Je cherche simplement à comprendre leurs workflows, pas à leur demander de recommander un produit qu'elles n'ont pas essayé.

Ne pas dire « preview prête » ou « démo validée » quand ce n'est pas le cas.

## Champs CRM à conserver hors Git

Identifiant organisation, segment, source, interlocuteurs et rôles, accord de contact, contexte Git/harness, mono-/multi-hôte, douleurs vérifiées, sponsor et décideur commercial, budget observé/inconnu, statut du partenariat, version et scénarios de test, alternatives réellement disponibles, risque de substitution, autorisations de publication, introductions attribuées, prochaine action, dates et preuves. Restreindre accès, minimiser les données personnelles, prévoir la possibilité d'opposition et respecter les règles de prospection B2B.

## Qualité des preuves

- **HYPOTHESIS** : affirmation à tester ;
- **SELF_REPORT** : réponse déclarative d'un prospect ;
- **OBSERVED** : action réellement observée ;
- **REPRODUCED** : test avec version, environnement, méthode et résultat ;
- **COMMERCIAL** : contrat, commande ou paiement dans le périmètre exact.

Le test de substitution a les états **U** (inconnu), **H1** (préférence hypothétique), **B2** (choix observé devant une alternative disponible) et **C3** (achat documenté malgré alternative disponible). Une préférence verbale ne devient pas une preuve comportementale.

## KPI hebdomadaires

| Indicateur | Sens |
| --- | --- |
| Comptes qualifiés | Problème réel + interlocuteur vérifiés |
| Entretiens tenus | Réunions réellement réalisées, pas invitations |
| Partenaires actifs | Accord réciproque + contribution constatée |
| Activation Core | Installation et scénario exécuté sur version identifiée |
| Usage récurrent | Activité observée dans deux périodes convenues |
| Pilotes Cloud actifs | Expérimentation multi-hôtes réellement lancée |
| Clients payants | Engagement commercial/paiement vérifié |
| Introductions converties | Nouveaux utilisateurs activés / introductions qualifiées |
| CAC, marge, rétention | Coût d'acquisition, service et maintien mesurés par cohorte |

Ne jamais substituer une cible à un résultat, compter plusieurs fois un même compte ou inférer des taux de croissance virale sans données. Une audience n'est pas une conversion.

## Boucle recherchée

Un utilisateur satisfait peut devenir source d'introduction ; une introduction acceptée peut activer un nouveau testeur ; une équipe adoptante peut devenir cliente Cloud ; un client satisfait peut autoriser un témoignage ou une intégration. Mesurer chaque passage et son coût. Le nombre de relations peut être grand, mais la collaboration intensive reste concentrée là où elle crée de la valeur.
